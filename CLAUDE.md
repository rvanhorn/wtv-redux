# Project instructions

The dotfiles setup command installs this file from the `javascript` profile and appends
`REPOSITORY.md` below the marker at the end. Edit `REPOSITORY.md` for a rule that is true for this
repository only, and edit the profile in the dotfiles repository for a rule that is true for every
basic JavaScript project. Do not edit this file directly; the next install replaces it. The global
instructions still apply; this file adds JavaScript project guidance.

## Orientation

Start with the affected implementation and the context needed to understand its behavior.
Read `package.json`, the committed lockfile, build configuration, entry points, source modules,
and tests when the change depends on them.
For generated output, find its authored source and generation command before changing it.
Identify whether the affected code runs in Node.js, a browser, another runtime, or more than one.
Use the applicable implementation examples and legacy exceptions in `REPOSITORY.md`.
Common existing code does not override an explicit preferred pattern.

## Ownership and boundaries

Keep code with its narrowest common owner.
Inspect consumers before a third copy of a small pattern.
Extract at a responsibility or test boundary; line count alone does not require extraction.
Keep entry points focused on composition and lifecycle.
Preserve dependency direction and public module boundaries.
Validate untrusted input at the boundary.
Normalize external data before it enters domain or UI code.
Preserve the source error when a boundary adds context.
Treat cancellation, shutdown, subprocess exit, and output draining as lifecycle behavior.

## Dependencies and generated state

Use the package manager selected by the committed lockfile. Do not add a second package manager.
If the project has no lockfile, use the package manager documented in `REPOSITORY.md` before
installing dependencies.
Record the required runtime and package-manager versions in the project manifest and
`REPOSITORY.md`.
Run scripts from the root or the affected package's `package.json`.
Record the exact test, lint, format, build, and repository gate commands in `REPOSITORY.md`.
Do not edit lockfiles or generated source by hand.
State a new dependency's purpose and material tradeoff before adding it.
Inspect scripts that format, fix, generate, or restage files before use.
Never suppress a check to make verification pass.
If an edit changes immediately or does not stick, inspect post-edit formatting hooks before
blaming the editor.

## Tests

Put a test with the source that owns the public behavior.
Keep unit, contract, integration, browser, and end-to-end scopes distinct.
Replace external providers with a contract-compatible fake in the regular suite.
Keep live provider checks separate and explicit.
Use explicit temporary roots for filesystem, database, and process tests.
Cover startup failure, degraded operation, cancellation, and shutdown when applicable.
Do not use elapsed time as the only proof that asynchronous work completed.
Set an explicit timezone or locale when a test depends on date or number formatting.
Test observable results and public contracts rather than private function calls or internal layout.
For applicable behavior, cover repeated mounting, cleanup, stale responses, keyboard interaction,
and persistence failure. Size the checks to the changed behavior and the repository's test policy.
If no test covers the changed behavior, use a focused reproduction and report the coverage limit.

# JavaScript conventions

## Vanilla JavaScript by default

Use JavaScript and the runtime's native APIs by default. Add a UI framework only when the project
explicitly selects one. A bundler, formatter, linter, or CSS framework does not require React or
another UI framework.
Use semantic HTML and native controls before building custom browser widgets.
Keep tooling proportional to the distribution requirements. A browser application can use native
modules without a bundler; a single-file distribution needs a build that combines its sources.

## Runtime and modules

Treat `package.json` as the source of truth for scripts, module format, public exports, and
runtime requirements.
Use ES modules (`import` and `export`) for new projects. Preserve an existing project's declared
module format unless migration is in scope. Do not mix ES modules and CommonJS without an explicit
interop boundary and a test that covers it. Distinguish source modules from the output format
required by the distribution runtime.
Declare supported browser and runtime versions in `REPOSITORY.md` and the relevant tool settings.
Select JavaScript syntax, CSS syntax, and APIs against those targets. Syntax transformation does
not supply missing runtime APIs; add a fallback or polyfill only when the supported targets need it.
Use the runtime APIs supported by the declared target. Keep Node.js, browser, and other runtime
adapters at their boundary.
Do not let a browser bundle depend on Node.js-only APIs, process state, or filesystem access.
Do not let a shared module import a server-only or UI-only implementation.

## Names and readable code

Apply the global descriptive-name rule to JavaScript bindings, callback parameters, functions,
exports, and files. Use `event`, `element`, `response`, and `configuration` instead of shorthand
such as `e`, `el`, `res`, or `cfg`. Keep a shortened name only when an external interface requires
it or it is an established domain term, such as `id` or `url`.
Name functions for their action and subject, such as `loadCatalog` or `savePreferences`.
Use predicate names such as `isLoading`, `hasSelection`, and `canSave` for booleans.
Make units and meaning visible where ambiguity matters, such as `timeoutMilliseconds`.
Name files for the responsibility they own. Avoid catch-all names such as `helpers.js` when a
specific name such as `date-format.js` describes the contents. Follow the project's filename case.

Use `const` for bindings that are not reassigned and `let` for those that are. Prefer strict
equality and explicit conversion at data boundaries. Use `??` when only `null` and `undefined`
mean missing; preserve valid `0`, `false`, and empty-string values.
Keep control flow readable. Split nested ternaries, compressed statements, and callbacks that
combine unrelated actions. Standard syntax such as `{ catalog }` is acceptable when the full
identifier makes the meaning clear; do not shorten names to save typing.
Prefer functions with explicit inputs and outputs. Make side effects visible at their owner,
avoid hidden global state, and keep transformations separate from I/O and DOM changes.
Put mechanical naming and style checks in the project's linter and formatter configuration.

## Comments explain constraints

First improve unclear names, control flow, or function boundaries. When code still cannot express
the reason for a constraint, document that reason in a comment near the affected code.
Explain non-obvious ordering, units, compatibility workarounds, invariants, and failure hazards.
Keep an external reference when it establishes the constraint. Do not narrate the next statement
or keep obsolete code in comments.
Use JSDoc when a public function's data shape, return value, side effect, or error contract is not
clear from its signature. Keep it accurate when the implementation changes. Do not add boilerplate
documentation to every function. Use JavaScript type checking when the project adopts it; JSDoc
does not require converting the project to TypeScript.

## Source organization

Keep the application entry point responsible for initialization, composition, and lifecycle.
Put business logic, data access, state, features, views, components, styles, and utilities in
modules with clear ownership when the project needs those boundaries.
The exact directory names are project choices. Do not create a directory only to satisfy a
taxonomy.
Keep authored files focused enough to understand and change one responsibility without reading
unrelated features. Split a growing file when it mixes responsibilities, independent lifecycles,
or separately testable behavior. Do not wait for a giant application file to form, and do not
replace it with a giant utility file. Generated bundles may be large; edit their source modules.
Use explicit imports to share behavior instead of copying it or exposing it through globals.
Export only the module's supported interface. Avoid circular imports. Let the entry point compose
modules and start application behavior explicitly instead of starting it through import side effects.
Intentional CSS imports and required platform setup imports are valid; keep their ordering explicit
where behavior depends on it.
Keep a helper local until another consumer or a meaningful boundary justifies extraction.
Remove obsolete implementations and imports made unused by an extraction.

Send network and external-service calls through an adapter or domain-owned client.
Convert external responses into application-owned data before other modules use them.
Keep views and components independent from transport formats and persistence implementations.
Keep state in one owner. Derive display values from that state instead of maintaining competing
copies in components or features.
Change shared state through its owner's operations so that validation and change notifications run
consistently. Consumers must not mutate shared objects or arrays through exposed references and
bypass those operations.
Use stable identifiers for references between records. Do not use display names as identifiers
when the source provides a stable key.

## JavaScript file organization

Apply this section to authored modules. It says how to split a file that the source-organization
rules say to split. Generated bundles are exempt.

- Name a module for the one responsibility it owns. When that responsibility needs more than one
  file, make a folder named for it with an `index.js` entry that composes the other files.
- Put a part that only its owner uses in `_components/` beneath the owner. A file outside the
  owner's folder does not import from `_components/`.
- Keep a short single-use helper inline. Put extracted pure helpers in a sibling `<name>.utils.js`.
- Keep a small single-use JSDoc type inline. Put a type that several files share in a sibling
  `<name>.types.js`.
- Export a factory `create<Name>(...)` from a part that holds state, listeners, or timers, and
  return its public functions from that factory. Export plain functions from a stateless part.
- Pass collaborators in explicitly. When parts call each other in both directions, the owner
  builds one shared context object, fills it in creation order, and documents its shape once.
  A part reads a collaborator from the context at call time, not at creation time.
- Order a module body as imports, module constants, private helpers, then exported functions.
  In an entry point, put composition and lifecycle last.

One factory whose inner functions all close over the same state is the vanilla equivalent of a
giant component. When its inner functions form groups that rarely call across the group boundary,
or a group has its own lifecycle, each group is a part. About 300 module lines or 15 helper lines
prompt a responsibility review, not an automatic split. Extract at a natural seam; preserve a valid
contract, invariant, or test boundary even when it has one consumer.

## Asynchronous behavior and errors

Make asynchronous boundaries explicit. Handle rejected promises at the boundary that can recover,
report, or terminate the operation.
For `fetch`, check the response status before consuming the expected payload. Validate external
data before committing it to application state.
Cancel obsolete requests with `AbortController` when supported, and reject stale results before
they update a replaced view or newer state. Treat expected cancellation separately from failure.
Use explicit deadlines when an operation must not wait indefinitely. Release timers and other
resources on success, failure, and cancellation.
Prevent duplicate submissions while an operation is pending. Bound concurrent requests when work
can grow with user input or collection size. Retry only when repeating the operation is safe;
use a bounded retry policy with delays and honor cancellation.
Preserve the original error as the cause when adding context.
Keep one failed request, feature, or optional integration from taking down unrelated behavior when
the product can continue safely.
Define loading, empty, partial, and error states for user-visible asynchronous work.
Use namespaced logs that identify the subsystem. Keep development diagnostics separate from
production output, and do not log credentials, tokens, or user data.

## Browser and user-interface code

Apply this section only when the project includes browser UI.

Use semantic HTML and preserve keyboard access, focus behavior, readable contrast, responsive
layout, reduced-motion preferences, and useful error states.
Keep reusable visual elements separate from screen-level composition.
Give each interactive component a clear creation, update, and cleanup contract. On removal,
unsubscribe from state, remove listeners, disconnect observers, clear timers, and cancel owned
work. Use `addEventListener` with an abort signal or explicit removal where appropriate.
Make repeated initialization safe: mounting twice must not duplicate UI, listeners, observers, or
timers. Cleanup must tolerate repeated calls and partially completed initialization.
Use `textContent`, `createElement`, and static HTML templates for DOM construction. Update the
affected nodes without losing focus, selection, or user-entered values. Use `classList` and
attributes for discrete visual states; use CSS custom properties for dynamic style values.
Keep DOM queries within the owning component when possible. Avoid repeated full-page scans and
alternating layout reads with writes in loops. Measure slow interactions before adding caches,
workers, or other performance machinery.
Use the browser History API or the project's router for navigation. Preserve Back and Forward
behavior and keep route changes separate from view implementation.
When embedded in another site, preserve the host's navigation and handlers. Use event listeners
instead of replacing shared `onpopstate` or other handler properties.
Do not insert untrusted strings as HTML. If rich HTML is required, use a maintained sanitizer
suited to the context. Validate untrusted URLs before assigning navigation or resource attributes.

## Modern CSS

Use native CSS by default. Organize styles by tokens, base rules, layout, components, and views
when the project needs those boundaries. Keep responsive rules with their owner when practical.
Use custom properties for shared design tokens and Grid or Flexbox for layout. Prefer logical
properties such as `margin-inline` and `padding-block` when layout follows the writing direction.
Use fluid sizing such as `clamp()` and container queries when a component depends on its available
space. Keep viewport media queries for viewport-level changes.
Use shallow native nesting where it clarifies ownership. Keep selectors low in specificity and
use cascade layers when explicit ordering of application and third-party styles is needed.
Use modern syntax such as `rgb(0 0 0 / 50%)`, range media queries, and `:focus-visible` where the
declared browser targets support it. Use `@supports` and fallbacks when enhancement is optional.
Preserve reduced-motion preferences and visible keyboard focus in every styling approach.
When embedded in another site, scope selectors and tokens to the application root, or use Shadow
DOM when its isolation fits the integration. Cascade layers alone do not isolate host styles.

## Optional CSS frameworks

Keep an existing styling system unless replacement is in scope. Choose a CSS framework only when
its benefits justify the dependency, and use documentation for the installed version.
Use its plain HTML and JavaScript integration. Check whether interactive components require a
separate JavaScript package, and include their initialization, accessibility, and cleanup contracts.
Compile generated framework CSS during development or the production build. Include the resulting
CSS in the deliverable; do not require a development CDN compiler in production.
For Tailwind, include the relevant HTML and JavaScript sources in class detection. Map state to
complete class names; do not construct names such as `bg-${color}-500`. Use custom properties for
values that are only known at runtime. Follow the installed version's source and theme configuration.
When embedded in another site, omit or isolate global resets such as Tailwind Preflight. Verify
that framework styles do not change the host page outside the application's intended scope.

## State and persistence

Hide browser storage, files, databases, or provider-specific storage behind a small adapter.
Keep persistence code out of presentation modules.
When the project stores user data, version the stored schema and provide deliberate migrations for
format changes.
When changing storage backends, migrate existing user data explicitly and preserve the old data
until the new write succeeds. Report persistence failure without claiming the data was saved.
Validate imported or externally supplied data before changing existing state.
Apply imports atomically: invalid or unsupported input must not partially replace valid data.
Keep reset and destructive data actions explicit and recoverable when the product supports it.

## Build and distribution

Keep authored source separate from generated output.
Define development and production commands in `package.json`. Development commands may watch,
preserve source names, and include diagnostics. Production commands must produce the artifact that
the stated runtime or user installs.
Do not require development tooling at runtime unless the product explicitly runs in that runtime.
When distribution requires one file, bundle the source modules without external runtime imports
or additional code chunks. Embed and load the built CSS explicitly; a JavaScript import alone does
not guarantee CSS injection. Check required assets and metadata in the final artifact.
Do not edit `dist/`, generated bundles, manifests, or other derived files by hand.
Record whether generated output is committed, ignored, or published by the repository's release
policy in `REPOSITORY.md`.
Inspect the build result, not only the build command's exit code, when a change affects packaging,
exports, bundling, or distribution.

## Versioning and release checks

Use the version format already selected by the repository. When a version appears in package
metadata, generated metadata, a changelog, or a release tag, update every required copy or
automate the synchronization.
Before a release, run the repository's checks, create the production artifact, inspect the
artifact's contents, and confirm that the artifact matches the intended source revision.

## Verification

| Change scope | Minimum final evidence |
| --- | --- |
| Policy or documentation | Narrow content or generation check |
| One module behavior | Focused test plus the affected package check |
| Shared module, export, or runtime boundary | Contract checks plus each affected consumer check |
| Browser behavior | Focused browser-mode test plus a local preview when available |
| Build, runtime, or package configuration | Affected checks plus the relevant build |
| Persistence, import, or migration | Valid, invalid, and upgrade-path checks |
| Commit or explicit repository verification | The named full repository gate |

Run formatting and lint checks after the final JavaScript edit.
Check each affected runtime target when a shared module changes.

# Repository rules

## Runtime and dependencies

Use Node.js 24 and pnpm 12. Install dependencies from `pnpm-lock.yaml` with:

```bash
pnpm install --frozen-lockfile
```

The installed userscript must have no runtime network dependency. Bundle required JavaScript and
CSS into the distribution file.

## Development and checks

Use these commands from the repository root:

- `pnpm run dev` rebuilds source and CSS and serves a loopback-only Greasemonkey or Tampermonkey loader for Firefox.
- `pnpm run check` checks JavaScript syntax, runs Oxlint, and verifies Oxfmt formatting.
- `pnpm run lint:fix` applies safe Oxlint fixes.
- `pnpm run format` formats supported repository files with Oxfmt.
- `pnpm run build` creates the production userscript.
- `pnpm run test` runs the development-server lifecycle tests and the deterministic Playwright Firefox suite.
- `pnpm run test:node` runs only the development-server lifecycle tests.
- `pnpm run test:browser` builds the userscript and runs only the Firefox suite.
- `pnpm run test:browser:headed` runs the browser suite for visible debugging.
- `pnpm run verify` runs the checks and the browser suite.
- `actionlint .github/workflows/*.yml` checks the workflows when `actionlint` is installed.

The development loader advances its revision only after a successful build. Run `pnpm run format`
and `pnpm run check` after the final edit. Run `pnpm run verify` before a commit or a release.

## Run browser checks through the shared browser server

Coding agents run shell commands inside a sandbox that denies access to the macOS window server.
Playwright's Firefox build aborts at startup without it, and macOS shows a crash dialog for each
attempt. Codex's `workspace-write` sandbox has this limit today. Claude Code's sandbox does not, but
the shared server keeps both agents on one path.

Start the server once from a normal terminal and leave it running:

```bash
pnpm run browser
```

It launches Playwright's Firefox with a visible window on `ws://127.0.0.1:7316/wtv-redux` and
writes `.playwright-server.json` at the repository root. While that file names a live process,
`pnpm run test`, `pnpm run test:browser`, `pnpm run verify`, and any script that uses
`playwright.config.js` connect to the running browser instead of launching one, so they work inside
an agent sandbox that allows loopback network access. Pass `--headless` to hide the window. Stop the
server with Ctrl+C; it removes the endpoint file. A stale file whose process has exited is ignored.

Before any Firefox process starts, `scripts/browser-launch.mjs` checks that the run can succeed.
When the endpoint file names a server, it checks that this shell can open a loopback connection to
it. When no server is running, it asks CoreGraphics whether this process may reach the window
server. If either check fails, the Playwright global setup and `pnpm run browser` stop with one
message that names the next step, and no Firefox process or crash dialog appears. The window-server
check runs a short `python3` probe; when `python3` is missing, the check passes and the run continues.

An ad hoc Playwright script must open Firefox the same way: import `openFirefox` from
`scripts/browser-launch.mjs` and call it in place of `firefox.launch()`. It connects to the running
server when one exists, launches Firefox when this shell may do so, and otherwise rejects with the
same message before any launch. A script kept outside the repository must import Playwright and
this module by their absolute paths under this repository, because a scratch location has no module
resolution for the project's dependencies.

Without the server, run the browser commands outside the agent sandbox. In Claude Code, that is the
Bash tool's option that disables the sandbox for one command. In Codex, that is a command approved
to run outside the sandbox. A Codex run with network access disabled has also been denied a loopback
`listen` call, so the shared server may be unreachable from that sandbox; the connection check
reports that case. Do not change the tests or the harness to work around a sandbox.

A local preview server started by a preview tool runs in its own sandbox and cannot read the
project directory, so serve copies of the needed files from the tool's scratch location instead.

## Tests must protect useful behavior

Keep all tests under `tests/`. Put browser tests and deterministic fixtures under `tests/browser/`.
Do not put test files beside source components.

Add or update a test when it can catch a plausible regression in observable behavior, a data
boundary, persistence, routing, lifecycle cleanup, or error handling. Prefer one focused test for
each changed behavior. Reuse the local Warhammer TV fixtures in the regular suite.

Do not add a test only to increase the test count, restate a constant, prove JavaScript behavior,
or lock in a private implementation detail. Keep live-site and authenticated checks separate from
the regular suite.

## Build and distribution

The browser bundle targets ES2020. `scripts/build.mjs` creates
`dist/WarhammerTV-Redux.user.js`. Generated files under `dist/` are ignored by Git and published as
GitHub Release assets.

## Versions and changelog

`package.json` owns the stable `major.minor.patch` version. The build inserts that version into the
userscript header.

Update the current `CHANGELOG.md` section for user-visible behavior, bug fixes, compatibility or
data-format changes, build or release process changes, and project identity changes. Do not add an
entry for spelling, formatting, or cleanup that changes no behavior, documented contract, or
release artifact. Add the entry in the same change. Describe the result and affected scope, not the
implementation steps.

See `README.md` for the release procedure and retry behavior.
